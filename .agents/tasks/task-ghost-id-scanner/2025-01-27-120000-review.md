# Ghost ID Scanner — visitor fingerprint display widget

The homepage's CONNECT section (social links to Instagram, Telegram, WhatsApp, Lynk.id Store) is replaced with a "Ghost ID Scanner" card that auto-fetches visitor metadata on page load and displays it in a terminal-style UI. A new Flask endpoint (`GET /api/ghost-scan`) extracts the visitor's IP, country, browser, language, and VPN status (via vpnapi.io) and returns them as JSON. The frontend animates through loading messages before revealing the data.

**Watch for:** The endpoint returns the visitor's raw IP address to the browser with no authentication or rate limiting (confirmed). The vpnapi.io call is made server-side with no timeout-based caching, so every page load burns an API credit and adds latency (confirmed). The endpoint is also accessible to any external client, not just the page's own fetch (confirmed).

## High-level view

The backend endpoint reads IP from the standard Cloudflare/proxy header chain, parses User-Agent with a basic string-match heuristic, and optionally calls vpnapi.io if `VPNAPI_KEY` is set. The design is straightforward but exposes the raw visitor IP in the JSON response body — any script on the page or external caller can harvest it. Other routes in this app hash the IP before using it, so this is an intentional departure from the existing privacy posture.

The frontend is a self-contained IIFE that waits for DOMContentLoaded, cycles through three cosmetic loading messages (800ms each), then fetches the endpoint. Error handling collapses to a "Scan Failed" text swap with no retry. The script assumes every element exists in the DOM and would silently exit if any ID is missing.

The VPN-detection path is gated behind an env var and wrapped in a bare `except Exception`, so it degrades to "Basic Scan Only" when the key is absent or the API fails. However, there is no caching: repeated page loads from the same visitor hit vpnapi.io every time, which will exhaust free-tier credits quickly and adds 200-500ms latency per request.

## IP exposure and abuse surface

The `/api/ghost-scan` endpoint returns the visitor's full IP address in the JSON body. This is unlike the `/track` endpoint, which hashes the IP with a salt before storing or using it. Because the ghost-scan endpoint has no authentication, no rate limiting, and no CORS restriction beyond the CSP `connect-src 'self'` (which only applies to browser fetch — curl ignores it), anyone can call it to retrieve the server-visible IP of any request origin.

For a personal portfolio site the risk is modest, but the pattern is unusual: most "what's my IP" services at least put the data behind a page render rather than a naked JSON API. If the site is behind Cloudflare, the CF-Connecting-IP header makes this accurate even through proxy layers.

The existing rate-limiting infrastructure (`_check_rate_limit`) is available but not applied here. Adding a per-IP cooldown would reduce bulk-scraping potential with minimal code.

## vpnapi.io integration — latency and cost

The vpnapi.io call (`requests_lib.get(..., timeout=5)`) happens synchronously on every request. The free tier allows 1,000 lookups/day. A page that auto-fires this on load will consume credits proportionally to unique visitors — and non-unique ones too, since there's no caching layer.

A simple in-memory cache keyed on IP with a 60-second TTL would eliminate redundant calls from the same visitor refreshing the page and reduce p99 latency from ~5s (timeout) to near-zero on cache hits:

```python
_ghost_cache = {}  # {ip: (timestamp, result)}
GHOST_CACHE_TTL = 60
```

The 5-second timeout is reasonable as a ceiling, but without caching it becomes a user-facing latency tax on every page load when the API is slow.

## Privacy note accuracy

The HTML contains:

```
Data ini hanya digunakan untuk menampilkan hasil scan di halaman ini.
```

("This data is only used to display scan results on this page.")

When `VPNAPI_KEY` is set, the visitor's IP is sent to `vpnapi.io` — a third-party service. The privacy note does not mention this. Whether this matters legally depends on jurisdiction, but the note is factually incomplete when VPN detection is active.

## Dead CSS from removed social-section

The diff adds `.ghost-scanner-section` rules to the responsive breakpoints but leaves the existing `.social-section` rules intact. Since the social-section HTML is gone, these are now dead rules. They don't break anything but add noise.

## Frontend error handling

The fetch `.catch()` handler swaps the loading text to "Scan Failed" but leaves the loading container visible and the results container hidden forever. There is no retry mechanism and no way for the user to trigger a re-scan. For a cosmetic widget this is acceptable, but worth noting that a network hiccup permanently breaks the section until the page is refreshed.
