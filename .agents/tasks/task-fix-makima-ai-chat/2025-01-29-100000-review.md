# MAKIMA AI chat with conversation history, persistence, and TTS

The MAKIMA AI chat feature gains multi-turn conversation context, client-side persistence, text-to-speech on AI responses, and proper error propagation from the Gemini backend. The backend endpoint now accepts a `history` array, maps it into Gemini's content format, and returns structured JSON errors with HTTP status codes instead of masquerading errors as AI replies. The frontend stores conversation in localStorage, sends the last 20 messages as context, and adds a CLEAR MEMORY button and per-bubble speaker button using the Web Speech API. Voice settings (five named options) are stored in localStorage but aren't wired to any synthesis parameter yet.

**Watch for:** Unbounded history payload from the client with no server-side size validation (confirmed). The `system_instruction` claims "ingat informasi penting" but memory is entirely client-side and easily cleared or manipulated (confirmed). The TTS toggle logic has a behavioral gap when clicking a *different* bubble's speaker while one is already playing (confirmed).

## High-level view

The backend maps client-sent history entries to Gemini's `{role, parts}` format and appends the current message. Error responses now use proper HTTP semantics (503 for unconfigured, 500 for generation failure, 429 for rate limit) instead of hiding failures inside `{reply: ...}`. The persona instruction now asks the model to "remember important information" — a promise that depends entirely on the context window being populated by the client on each request.

The frontend adds localStorage as the persistence layer with no size cap. The TTS implementation provides a stop-on-second-click pattern but doesn't handle the case where a user clicks a different bubble's speaker while speech is already in progress — it cancels and returns without starting the new one.

The history payload sent to the server is completely client-controlled with no server-side size or structure validation beyond the 20-entry slice. A malicious or buggy client can send arbitrarily large history entries that inflate the Gemini API call.

<summary>Issues (4)</summary>

1. **No server-side history size validation** — The backend trusts the client's `history` array without checking total payload size or individual entry lengths. Add a max total character count across all history entries (e.g., 40,000 chars) and reject with 400 if exceeded.
2. **TTS toggle gap on cross-bubble click** — Clicking a speaker button on bubble B while bubble A is still speaking cancels speech and returns early without starting B's speech. The user must click B again. Either auto-start B after canceling A, or document this as intentional.
3. **localStorage growth is unbounded** — Chat history accumulates forever with no cap. Once localStorage fills (~5MB), saves silently fail. Add a max-entry cap (e.g., 200 messages) and trim oldest entries on save.
4. **History role injection** — Client can send entries with `role: 'model'` directly, injecting arbitrary "AI" context that shapes Gemini's responses. This is low severity for a character chatbot but worth noting if the persona ever needs to enforce trust boundaries.

## History context and Gemini content construction

The backend takes the `history` array from the request body, slices the last 20 entries, and maps `'assistant'` to `'model'` and `'user'` to `'user'` before appending the current message. The `contents` list is passed directly to `generate_content()`, replacing the previous single-string call.

There's no validation on the *size* of each history entry's text field. The frontend enforces a 2000-character limit on the *current* message, but history entries bypass this entirely. A client could send 20 entries each with 100KB of text, blowing up the Gemini token count and potentially hitting API quota limits or causing timeout errors. The fix is straightforward — sum the character lengths of all history texts and reject early if a threshold is exceeded.

The `system_instruction` says "Ingat informasi penting yang user berikan selama percakapan." The model has no persistent memory — it only sees what the client sends in the `history` field each time. The phrasing could mislead users into thinking persistence exists server-side when it's entirely client-controlled localStorage.

## TTS toggle behavior

The `_speakMakimaText` function checks `window.speechSynthesis.speaking` — if true, it cancels and returns. Clicking a *different* bubble's speaker while one is playing will stop the current speech but won't start the new one. The user must click the second bubble again. The fix: after canceling, check if the cancel target is the same button (stop) or a different button (switch), and only return early for same-button clicks.

The voice setting stored in localStorage is never passed to `SpeechSynthesisUtterance` — these are placeholders for future Gemini TTS integration, so current TTS uses whatever Indonesian voice the browser provides by default.

## localStorage persistence and bounds

Chat history grows unbounded. Each message adds a `{role, text}` object to the array. For a user who chats frequently, this will eventually hit the ~5MB localStorage quota per origin. When that happens, `_saveMakimaHistory()` silently catches the exception and the history diverges from what's displayed — new messages appear in the UI but aren't persisted, so a page reload loses them.
